JavaScript¶

The JavaScript runner executes under Node.js (V8) and compares built-in C++ JSON (JSON.stringify / JSON.parse) and structured-clone binary (node:v8) against pure-JS and native-addon libraries for MessagePack, CBOR, BSON, Ion, AMF, YAML, TOON, three Protocol Buffers runtimes, Avro, FlatBuffers, Dagr, Arrow IPC, Parquet, and WebAssembly HDF5.

Runtime & Environment¶

Measurements run on the Node.js CLI host (not a browser engine), embedding Google's V8 JavaScript engine with optimizing JIT compilation, generational garbage collection, Buffer, and optional C++ native addons. Timings are collected with performance.now() and converted to nanoseconds. Hot functions optimize after initial calls, and codecs that reuse Encoder / Packr instances (cbor-x, msgpackr) avoid per-call allocation overhead. The language is specified by ECMA-262 and the host runtime by the Node.js API documentation.

Property Configuration

Library background & provenance

Origin and design rationale for each registered library. Links point to upstream repositories, standard-library paths, or in-tree reference implementations.

  • @msgpack/msgpack — The official MessagePack JavaScript implementation (@msgpack/msgpack). MessagePack was created as compact binary JSON. This package is the reference encode/decode API for JS.
  • amf-codec — amf-codec is a small AMF0 encoder and decoder for Node. AMF0 is the command encoding inside RTMP. The timed path is toAMF and fromAMF on one plain object. It does not write AMF3.
  • arrow-ipc — Apache Arrow was created so analytic engines could share columnar batches without copying each one into a private layout. The problem was a convert-at-every-boundary tax. Arrow IPC is the stream format for those batches. This row times the apache-arrow IPC stream writer and reader (tableToIPC with type stream) inside the suite's bytes mode, not the Arrow file format. Schema objects are selected in prepare. Row-to-column conversion stays inside serialize. table_project deserialize reads f_float_0 only. No compliance decoder.
  • avsc — avsc brings Apache Avro to JavaScript. Avro was created for compact, schema-driven records in data pipelines. avsc solves the JS side with Type.forSchema and buffer encode/decode.
  • bebop — Bebop is a schema-driven binary format created as a simpler, faster alternative to protobuf-like IDL stacks for games and services. The problem was heavy generated code and slow encoders. Bebop solves it with a compact schema and generated writers.
  • biorate-amf — @biorate/amf is an AMF3 encoder and decoder for JavaScript. AMF3 adds a short integer and shared strings. The timed path is encode and decode on one plain object. It is a separate row from amf-codec because that library writes AMF0.
  • bser — BSER is Facebook Watchman's binary protocol: a compact encoding for the watchman's client/server messages. The problem was JSON overhead in a local file-watching daemon. This row times the Node bser dump/load path.
  • bson — BSON (Binary JSON) was created for MongoDB so documents could be stored and traversed without a text parse. Official language drivers implement that spec. This row times that library's serialize/deserialize path.
  • cbor — node-cbor implements IETF CBOR (RFC 8949) for Node. CBOR exists as the IETF's binary JSON-like format. The library is a full encode/decode implementation of that RFC.
  • cbor-x — cbor-x is a high-performance CBOR encoder/decoder for JS, from the same author as msgpackr. The problem was slow or allocating CBOR stacks in Node. It solves that with reusable Encoder/Decoder instances.
  • dagr-frozen, dagr-frozen-packed, dagr-packed, dagr-regular — Dagr ("Data Graph") is a schema-driven binary format that can store shared nodes and cycles, built on an arena model. One Python DSL schema generates the code for every target language (dagr build), so there is no runtime library: the suite commits the generated code from schemas/v2/dagr/schema.py. The five suite types are emitted in all four node layouts, one row each. The graph data type is emitted only for regular and frozen, because a packed reference cannot store the person ring. On suite types, prepare builds the native value and the timed call writes every field (direct builder or arena serializer) and reads them back.
    • dagr-frozen: This row uses the frozen node layout (positional, no evolution). It also times the graph data type.
    • dagr-frozen-packed: This row uses the frozen+packed node layout (positional and inline, no evolution). It does not support the graph data type.
    • dagr-packed: This row uses the packed node layout (tagged, evolvable). It does not support the graph data type.
    • dagr-regular: This row uses the regular node layout (vtable, evolvable). It also times the graph data type.
  • devalue — devalue was written (SvelteKit and friends) to stringify richer JavaScript values than JSON allows — dates, maps, cyclical graphs — without eval. The problem was JSON's limited types and eval-based hydrators. devalue solves it with a custom text format.
  • fast-json-stringify — fast-json-stringify was created in the Fastify ecosystem to serialize JSON from a JSON Schema much faster than JSON.stringify. The problem was that schema-known objects still paid for a fully dynamic walk. It compiles a serializer once and reuses it; this suite decodes with JSON.parse.
  • flatbuffers — FlatBuffers was created at Google so games and clients could access serialized data without an unpack step. The problem was that protobuf-style decode allocated a full object graph. FlatBuffers solves it with a schema and a binary layout that can be traversed in place.
  • flexbuffers — FlexBuffers is the schemaless cousin of FlatBuffers. It was created so you can have a FlatBuffers-family binary without compiling a schema. The same Google repository implements it.
  • fory — Apache Fory (formerly Fury) was created for high-performance, cross-language serialization. The problem was that JVM-centric binary codecs and slow portable formats left a gap. Fory registers types and serializes with a compact binary protocol. This row uses @apache-fory/core with registered struct/list schemas and the bytes API.
  • gld-kiln — gld-kiln (leo-gan) is a positional little-endian codec. The timed path reuses one writer. There are no field tags on the wire. This row times encode and decode of the suite structs. On the tensor data set this row runs every type. tensor_view borrows the float32 payload and does not copy the matrix.
  • gld-kiln-asm — gld-kiln-asm (leo-gan) is a pure x86-64 Assembly (GNU as) Kiln Wire Format v2 library with AOT schema codegen (gld_kilngen_asm.py) bound via Node.js N-API addon statically linking shared libkiln_asm_bench.a. Covers suite, columnar (TableColumns with KILN_OPT_EMBEDDED O(1) column-skip for table_project), array (KLNT v2 grid + strided grid_window), and tensor (KLNT v2 with zero-copy Buffer.subarray tensor_view).
  • google-protobuf — This is Google's official JavaScript protobuf runtime (google-protobuf / jspb). It exists so the same .proto contracts can run in JS. The suite times serializeBinary / deserializeBinary.
  • h5wasm — h5wasm compiles HDF5 to WebAssembly. This row times one float64 dataset named grid in the WASM memory filesystem. grid_window reads a dataset slice, which is a libhdf5 hyperslab. The row does not time the five suite types.
  • ion-js — Amazon Ion was created at Amazon as a rich, self-describing superset of JSON (text and binary) for internal services. The problem was JSON's limited types. ion-js is the official JavaScript implementation. This row times binary dump/load; the Ion DOM is turned into plain objects outside the timer.
  • js-yaml — js-yaml is the usual Node YAML 1.2 parser/dumper. YAML exists as a human-friendly config language. js-yaml solves the JavaScript side with a widely deployed implementation.
  • json-pack-msgpack — json-pack (jsonjoy) is a family of binary codecs including MessagePack. It was written to give JavaScript a fast, modular binary JSON toolkit. This row times the MsgPack encoder/decoder.
  • JSON.stringify — JSON.stringify / JSON.parse are the ECMAScript standard JSON APIs. They exist so every JavaScript host can speak RFC 8259 without a library. This row times Node's V8 implementation.
  • msgpackr — msgpackr was written for high-throughput MessagePack in Node, with reusable Packr/Unpackr instances. The problem was that generic MessagePack libraries allocated too much per call. msgpackr solves that with a performance-oriented encoder/decoder.
  • parquet — Apache Parquet was created as a columnar file for scans that touch a few fields of many rows. The problem was row files that made every reader parse every column. This row times hyparquet-writer parquetWriteBuffer at the library default codec, Snappy, and hyparquet 1.31.2 parquetReadObjects. A nested_table value (struct plus a list of structs, int32 not widened) round-tripped, which is why the row is registered. table_project passes columns ['f_float_0'] on read. SerializerVersion is the writer package. No compliance decoder.
  • parquet-uncompressed — This is the same hyparquet-writer path as parquet, with codec UNCOMPRESSED. That switch changes the column codec metadata and the bytes. Encodings stay at the library default. It is the same writer, not a second Parquet library. No compliance decoder.
  • protobuf-es — protobuf-es is Buf's Protocol Buffers implementation for ECMAScript. The problem was that existing JS protobuf stacks did not match modern TypeScript and the official proto3 feature set. It generates TypeScript and times toBinary / fromBinary.
  • protobufjs — protobuf.js is a popular JavaScript Protocol Buffers implementation that can work from a .proto or a JSON descriptor. The problem was that Google's JS protobuf was awkward in Node. protobuf.js solves it with a JS-native API.
  • sia — Sia is Timeleap's compact binary tag format for JS values. It was created as a project-specific, typed binary encoding rather than a public interchange standard. This row times those primitive writers.
  • simdjson-parse+JSON.stringify — simdjson was created to parse JSON at memory-bandwidth speeds using SIMD. The problem was that conventional parsers were far from hardware limits. This row uses simdjson only for parse; serialize is still JSON.stringify.
  • toon — @toon-format/toon is the official TypeScript codec and the reference for TOON specification 4.4. The timed path is encode and decode of UTF-8 text. The Size column is that byte length. A token count is not part of the measurement.
  • v8-serializer — Node's v8.serialize / v8.deserialize snapshot V8 values. They exist so the engine can persist structured clones, not as a portable wire format. This row times that Node-only API.

Measurement Caveats¶

  • Bytes-only runner: Every JavaScript adapter operates on in-memory buffers; the runner does not emit stream rows so no adapted stream is misreported as streaming I/O.
  • Optional native addon (simdjson): simdjson-parse+JSON.stringify registers only when the native simdjson addon loads. Its row name explicitly discloses that encode remains JSON.stringify.
  • Non-portable formats: v8-serializer and devalue are Node.js/JavaScript-specific value encodings rather than cross-language wire standards.
  • Protobuf schema source: protobuf-es and google-protobuf generate stubs from javascript/schemas/js_fixtures.proto (matching JS shapes with string timestamps).
  • Dagr bundling & decode path: dagr build emits TypeScript bundled via esbuild into src/generated/dagr_bundle.js. Direct builders (dagr-packed, dagr-frozen-packed) and arenas (dagr-regular, dagr-frozen) are prepared in prepare(), writing into a reused Builder; decode materializes domain values from lazy accessors inside the timed path, with \(N > 1\) framed as [u32 count][u32 len][record].
  • Columnar libraries: parquet uses hyparquet-writer 0.16.10 + hyparquet 1.31.2 (parquet-wasm is not registered). Row-to-column conversion runs inside timed serialize per Timing contract rule 8.
