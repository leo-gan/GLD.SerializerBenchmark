C¶

C serialization is decentralized: each library defines its own memory and object model—DOM trees, streaming encoders, or generated C structs—with manual allocation and no shared runtime reflection.

Runtime & Environment¶

The C runner compiles C11 source code to a native binary via CMake in the Release configuration (gcc or clang). Memory is managed explicitly by each library or by runner-owned buffers, with no virtual machine, JIT warmup, or garbage-collection pauses. Compiler selection and optimization flags (-O) dominate absolute throughput; Debug builds are not comparable to published Dashboard numbers. The language is specified by ISO/IEC 9899 (C11 draft N1570; reference at cppreference).

Registered Serializers¶

Map-oriented codecs (JSON, MessagePack, CBOR, BSON, Ion) share a single visitor in c/src/v2_codec.c so adapters implement only library primitives rather than hard-coding domain graphs. A serializer registers only when CMake links its library (serializer: … REAL).

Library background & provenance

Origin and design rationale for each registered library. Links point to upstream repositories, standard-library paths, or in-tree reference implementations.

  • avro-c — Apache Avro was created for Hadoop-era data: a compact binary encoding with the schema stored out of band so field names are not repeated. avro-c is the official C implementation of that encoding.
  • cJSON — cJSON was written as an ultralightweight JSON parser in ANSI C for embedded and application code that could not afford a heavy toolkit. The problem was that existing C JSON stacks pulled large dependencies or a C++ runtime. cJSON solves that with a single-file DOM: parse to a tree of cJSON nodes, mutate, and print.
  • custom-binary — This is the suite's length-prefixed V2 baseline, not a published format. It exists so every language has a simple binary control point: write fields with explicit lengths, read them back, no schema compiler.
  • flatcc — flatcc is the maintained C implementation of FlatBuffers. FlatBuffers was created at Google so games and other clients could read serialized data without a parsing/unpacking step. flatcc solves the C side with a schema compiler and a C builder/reader.
  • gld-kiln — gld-kiln (leo-gan) is a positional little-endian codec. The timed path reuses one writer. There are no field tags on the wire. This row times encode and decode of the suite structs. On the tensor data set this row runs every type. tensor_view borrows the float32 payload and does not copy the matrix.
  • gld-kiln-asm — gld-kiln-asm (leo-gan) is a pure x86-64 Assembly (GNU as) Kiln Wire Format v2 library with AOT schema codegen (gld_kilngen_asm.py) linked via shared libkiln_asm_bench.a. Covers suite, columnar (TableColumns with KILN_OPT_EMBEDDED O(1) column-skip for table_project), array (KLNT v2 with strided window copy), and tensor (KLNT v2 with zero-copy tensor_view).
  • hdf5 — The HDF5 C API is the baseline the other bindings call. This row times one contiguous float64 dataset named grid on the core virtual file driver. The byte size is the flushed file image. grid_window reads an interior hyperslab. The row does not time the five suite types.
  • ion-c — Amazon Ion was created at Amazon as a rich, self-describing superset of JSON (text and binary) for internal services. The problem was JSON's limited types. ion-c is the official C implementation. This row times the binary writer and reader on the suite visitor, including a native FILE* stream.
  • jansson — Jansson was created to give C a complete, documented JSON library with a stable API — encode, decode, and manipulate values — not just a minimal parser. The problem was that many C JSON snippets were incomplete or awkward to embed. Jansson solves it with a reference-counted value type and an API aimed at RFC 8259.
  • json-c — json-c is a long-running C implementation of JSON intended to be the practical library for Unix/C programs. The problem was the lack of a maintained, RFC-oriented JSON C library for system software. It solves that with a C API that aims at RFC 8259.
  • libbson — libbson is MongoDB's C library for building and iterating BSON documents. BSON exists so MongoDB can store JSON-like documents with a binary, traversable layout. libbson solves that with bson_append_* / bson_iter_*.
  • libcbor, libcbor-stream — libcbor is a CBOR protocol implementation for C targeting RFC 7049 and RFC 8949. The problem was the need for a full-featured C CBOR DOM and streaming encoder. It solves that with cbor_load for documents and cbor_encode_* for streaming.
    • libcbor-stream: This row times libcbor's streaming cbor_encode_* API, not the DOM cbor_load decoder.
  • libyaml — libyaml is the official C library for YAML 1.1, written so other languages (PyYAML, Yams, ext-yaml) can share one parser/emitter. YAML exists as a human-friendly config language. This row times the C library directly.
  • mpack — MPack is a C encoder/decoder for MessagePack, aimed at correctness and a clean buffer/stream API. The problem was that C MessagePack options were either incomplete or awkward to embed. MPack solves it with a documented pack/unpack implementation of the MessagePack spec.
  • msgpack-c — msgpack-c is the official C/C++ implementation of MessagePack. MessagePack was created to be as small and fast as a binary format while staying as simple as JSON. The C library solves that with pack/unpack APIs (and a separate C++ API in the same repository).
  • nanopb — nanopb was written so Protocol Buffers could run on microcontrollers. The problem was that Google's C++ protobuf runtime is far too large for tiny devices. nanopb solves it with a small C implementation and a generator aimed at static allocation.
  • parson — Parson was written as a small, single-file JSON library in C that is easy to drop into a project. The problem was boilerplate-heavy C JSON stacks. Parson solves it with a compact DOM around json.org JSON.
  • protobuf — Protocol Buffers were created at Google so many languages could share a compact, evolving binary contract without hand-written parsers. The problem was ad-hoc binary formats and verbose XML. Protobuf solves it with an IDL, generated code, and a documented tag/length wire format.
  • protobuf-c — protobuf-c provides C bindings for Google Protocol Buffers. The problem was that official protobuf was C++-first. protobuf-c solves it with protoc-gen-c and a C runtime for the same wire format.
  • protobuf-wire — This row is the suite's in-tree proto3 tag reader/writer. It exists to measure the published Protocol Buffers encoding itself, without a particular vendor runtime. Field numbers match schemas/v2/protobuf/benchmark_v2.proto.
  • qcbor — QCBOR was written as a comprehensive, safety-oriented CBOR implementation for professional and embedded use (RFC 8949). The problem was that CBOR stacks were either incomplete or hard to audit. QCBOR solves it with a carefully bounded C encoder/decoder.
  • tinycbor — Intel TinyCBOR was written so constrained and systems software could speak IETF CBOR (RFC 7049 / 8949). The problem was that CBOR needed a small, well-specified C encoder/decoder. TinyCBOR solves it with a buffer-oriented C API.
  • ubj — This row is the suite's in-tree UBJSON marker codec around the V2 binary payload. UBJSON was created as a binary cousin of JSON with explicit types. The harness implements the markers so C has a UBJSON size/speed point without a third-party dependency.
  • yyjson — yyjson was written for high-performance JSON in ANSI C: fast parse and print without giving up a usable DOM. The problem was that lightweight C parsers were slow, and fast parsers were often C++ or SAX-only. yyjson solves that with a compact C implementation and mutable/immutable document APIs.
  • zcbor — Nordic zcbor was created to generate C from CDDL and to encode/decode CBOR on constrained devices. The problem was writing CBOR by hand against a schema. zcbor solves it with a CBOR codec plus a CDDL code generator.

Measurement Caveats¶

  • Stream honesty: Stream mode uses an in-memory FILE* (fmemopen). Only ion-c and yyjson bind library FILE* callbacks (StreamMode=native); all other stream rows copy an already-encoded buffer (StreamMode=adapted).
  • Protobuf family scope: protobuf times official Google libprotobuf generated from schemas/v2/protobuf/benchmark_v2.proto. By contrast, nanopb, protobuf-c, and protobuf-wire currently share the in-tree fixture_pb_v2.h wire encoder/decoder; do not interpret them as full generated-code benchmarks of those upstream runtimes (see 4.5 C: protobuf-c and 4.6 C: nanopb vs. protobuf-c for the library internals).
  • Payload-wrapped rows: ubj, flatcc, and avro-c wrap the V2 binary payload inside a small envelope rather than generating full multi-type schemas.
  • Decoder caveat on libcbor-stream: Only encode uses the streaming cbor_encode_* API; decode still calls DOM cbor_load.
  • Symbol prefixing: parson and tinycbor are linked with prefixed symbols so they coexist with jansson and libcbor in one binary.
  • Separation from C++: C and C++ runners use distinct object models and build toolchains; see C vs. C++ separation.
