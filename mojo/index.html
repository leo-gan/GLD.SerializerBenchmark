Mojo¶

The Mojo runner evaluates pure-Mojo serialization libraries across community packages (EmberJson, ehsanmok/json, DataBooth/mojo-toml), generated Dagr graphs, and from-scratch pure-Mojo gld-* implementations covering JSON, TOML, YAML, CBOR, BSON, MessagePack, Ion, Smile, Protocol Buffers, FlatBuffers, Avro, Kiln, Arrow IPC, Parquet, HDF5, NetCDF, and ADIOS2.

Runtime & Environment¶

Mojo compiles ahead of time to native machine code using compiler-managed ownership rather than a tracing garbage collector. Because Mojo 1.1 is an evolving compiler, toolchain updates or pixi lock changes can shift absolute latencies significantly. Vendored gld-* packages rename internal runtime modules (cbor_runtime, pb_runtime, avro_runtime, gldjson, gldtoml, ehsanmok_json) so all libraries compile into one process without namespace collisions. Language semantics are documented in the Mojo Language Reference and Mojo Manual.

Library background & provenance

Origin and design rationale for each registered library. Links point to upstream repositories, standard-library paths, or in-tree reference implementations.

  • arrow-ipc — Apache Arrow was created so analytic engines could share columnar batches without copying each one into a private layout. The problem was a convert-at-every-boundary tax. gld-arrow (leo-gan) is a from-scratch Arrow library for Mojo. This row times encode_ipc_stream and decode_ipc_stream: the IPC stream, not the Arrow file. The record batch is built inside serialize. gld-arrow has no included-fields reader, so table_project decodes the stream and then materializes f_float_0 only. Suite columns are required because these rows have no nulls.
  • dagr-frozen, dagr-frozen-packed, dagr-packed, dagr-regular — Dagr ("Data Graph") is a schema-driven binary format that can store shared nodes and cycles, built on an arena model. One Python DSL schema generates the code for every target language (dagr build), so there is no runtime library: the suite commits the generated code from schemas/v2/dagr/schema.py. The five suite types are emitted in all four node layouts, one row each. The graph data type is emitted only for regular and frozen, because a packed reference cannot store the person ring. On suite types, prepare builds the native value and the timed call writes every field (direct builder or arena serializer) and reads them back.
    • dagr-frozen: This row uses the frozen node layout (positional, no evolution). It also times the graph data type.
    • dagr-frozen-packed: This row uses the frozen+packed node layout (positional and inline, no evolution). It does not support the graph data type.
    • dagr-packed: This row uses the packed node layout (tagged, evolvable). It does not support the graph data type.
    • dagr-regular: This row uses the regular node layout (vtable, evolvable). It also times the graph data type.
  • ehsanmok-json — ehsanmok/json is a Mojo JSON parser/serializer. It was written to give Mojo a JSON stack with a Value tree and a serialize_json path. Decode in this suite is loads plus a Value walk.
  • EmberJson — EmberJson is a Mojo JSON library using language reflection. Mojo is a young language; EmberJson exists to give it a community JSON serialize/deserialize path. This row times that reflection API.
  • gld-adios2 — gld-adios2 (leo-gan, bundled in gld-hdf5) is a pure-Mojo ADIOS2 BP5 directory encoder and decoder framed into in-memory bytes for float64 variables on the suite types.
  • gld-hdf5 — gld-hdf5 is a from-scratch HDF5 library for Mojo. HDF5 exists to store typed arrays in a portable file. This row times one contiguous float64 dataset named grid. The first dimension is x and the second is y. grid_window copies the interior window after read_hdf5 returns the whole file, because this library has no hyperslab. It does not link libhdf5 and does not time the five suite types.
  • gld-kiln — gld-kiln (leo-gan) is a positional little-endian codec for Mojo. The encoder is generated from the struct fields at compile time and writes into a reused buffer. This row times encode and decode of the suite structs. There are no field tags on the wire. On the tensor data set this row runs every type. encode writes the struct. tensor_view uses Reader.take and does not copy the matrix.
  • gld-kiln-asm — gld-kiln-asm (leo-gan) is a pure x86-64 Assembly (GNU as) Kiln Wire Format v2 library with AOT schema codegen (gld_kilngen_asm.py) loaded via OwnedDLHandle against shared libkiln_asm_bench.so. Covers suite, columnar (TableColumns with KILN_OPT_EMBEDDED O(1) column-skip for table_project), array (KLNT v2 with strided window copy), and tensor (KLNT v2 with zero-copy tensor_view).
  • gld-netcdf — gld-netcdf (leo-gan, bundled in gld-hdf5) is a pure-Mojo NetCDF-4 writer and reader using distinct dimension and variable names for float64 datasets on the suite types.
  • gld-toml — gld-toml (leo-gan) is a from-scratch TOML 1.1 library for Mojo. It is not DataBooth/mojo-toml. The benchmark vendors it as gldtoml so its package name does not collide with DataBooth's toml package.
  • gld-yaml — gld-yaml (leo-gan) implements YAML encode/decode for Mojo. YAML exists as a human-friendly config language. The library was written so Mojo can speak YAML on suite types.
  • mojo-avro — gld-avro (leo-gan) implements Apache Avro for Mojo via AvroDatum. Avro exists for compact, schema-driven records. The library gives Mojo that encoding.
  • mojo-bson — gld-bson (leo-gan) is a from-scratch BSON codec for Mojo. BSON exists so MongoDB can store JSON-like documents in a binary, traversable layout. This row times WireWriter / WireReader on suite types.
  • mojo-cbor — gld-cbor (leo-gan) implements CBOR for Mojo via a CborDatum trait. CBOR is the IETF binary JSON-like format. The library exists to give Mojo a first-class CBOR encode/decode.
  • mojo-flatbuffers — gld-flatbuffers (leo-gan) is a FlatBuffers implementation for Mojo. FlatBuffers exists so a reader can take fields from the buffer without first copying the whole message into a new object. This row keeps one Builder, calls clear before each message, and times generated pack / unpack against the suite tables in cpp/schemas/benchmark.fbs.
  • mojo-ion — gld-ion (leo-gan) is a from-scratch Amazon Ion codec for Mojo. Ion exists as a typed superset of JSON with text and binary encodings. This row times Ion 1.0 binary encode and decode of a document built from the suite value.
  • mojo-json — gld-json (leo-gan) is a typed JSON WireWriter/Reader for Mojo. It was created because Mojo lacked a suite-ready, typed JSON codec aligned with this benchmark's domain types.
  • mojo-msgpack — gld-messagepack (leo-gan) is a MessagePack WireWriter/Reader for Mojo. MessagePack exists as compact binary JSON. The library gives Mojo that format.
  • mojo-protobuf — gld-protobuf (leo-gan) is a Protocol Buffers implementation for Mojo. Protobuf exists as a language-neutral IDL. This library generates Mojo from the suite .proto and times encode/decode.
  • mojo-smile — gld-smile (leo-gan) is a from-scratch Smile codec for Mojo. Smile exists as a compact binary form of JSON. This row times encode_doc and decode_bytes on a document built from the suite value.
  • mojo-toml — DataBooth/mojo-toml is a TOML library for Mojo. TOML exists as an obvious config language. This row times that library. leo-gan/gld-toml is a different library and is the gld-toml row.
  • parquet — Apache Parquet was created as a columnar file for scans that touch a few fields of many rows. The problem was row files that made every reader parse every column. gld-parquet (leo-gan) is a from-scratch Parquet library for Mojo. The library default is uncompressed, so this row sets Snappy, the suite page codec. table_project decodes the file and then reads f_float_0 only, because decode_table has no column projection. Lists use the standard three-level group.
  • parquet-uncompressed — This is the same gld-parquet writer as parquet, with the page codec left uncompressed. Encodings stay at the library default. The name is the override.

Measurement Caveats¶

  • Dagr conversion boundary: In Mojo, conversion from suite structs into Dagr direct builders (dagr-packed, dagr-frozen-packed) or arenas (dagr-regular, dagr-frozen) is currently timed inside serialize; decode materializes suite values from lazy readers. Regenerate src/gen/dagr/ via dagr build in schemas/v2/dagr/ rather than editing generated files.
  • No partial-read projection in gld-* array/columnar codecs: gld-hdf5 lacks hyperslab reads (grid_window slices after reading the whole file), and gld-arrow / gld-parquet lack column-pruning readers (table_project decodes before projecting f_float_0).
  • Kiln compliance vs. timed version: Compliance tests score Kiln wire v2 with gld-kiln 0.3.0; the timed Mojo benchmark row pins gld-kiln 0.2.0.
  • Package pins and exclusions: EmberJson pins the Modular community 0.3.4 release (not newer from_json/to_json main). ehsanmok/json stubs GPU/max and times the CPU path. No native XML library is registered; f0cii/mojo-csv does not compile on Mojo 1.1, and forfudan/decimojo is a decimal math library rather than a standalone serializer.
